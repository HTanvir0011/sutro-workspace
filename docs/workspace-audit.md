### Are RS and BS records paired? Yes (synthetic set)

Verified in `sutro-dataset/khatian_form5462/`:

- `khatians.csv` (`khatian_id, land_id, split, version_idx, survey, year, khatian_no, sheet_no, n_owners, n_dag_rows, total_land_dec, image_file`): **2,000 lands × 2–4 versions** (2 versions: 678 lands, 3: 850, 4: 472) = 5,794 khatians; surveys CS 1,104 / SA 1,775 / RS 1,776 / BS 1,139; survey sequences per land: CS>SA>RS>BS 472, SA>RS>BS 442, CS>SA>RS 408, SA>RS 229, RS>BS 225, CS>SA 224. Year ranges CS 1890–1940, SA 1950–1968, RS 1968–1996, BS 1998–2021; 0 lands with non-increasing years.
- `title_line.csv` (`land_id, split, from_khatian_id, to_khatian_id, from_survey, to_survey, transition, detail_json`): 3,794 consecutive-version links, of which **RS→BS 1,139** (one per BS khatian), SA→RS 1,551, CS→SA 1,104. Transition ground truth: inheritance 1,726, sale 890, inheritance+sale 758, none 420 (RS→BS: 593 / 236 / 164 / 146). `detail_json` holds the parties, fractions and inheritance basis.
- `owners.csv` gives each owner's exact share per version (`share_exact` fraction, `share_printed_3dp`), so share changes between RS and BS are checkable against the recorded cause.
- Splits are **by land**: 0 lands appear in more than one split (train 4,645 / val 570 / test 579 khatians).

**No real RS/BS khatian dataset is publicly available.** The only research release found, KhatianDoc (107 RS khatians, Munshiganj), had an empty Hugging Face repository when checked on 2026-10-15. Government portals (land.gov.bd, eporcha) are one-record lookups and must not be scraped (§8). Hence the paired data is synthetic.

## 5. Unknowns and risks

1. **`DATASET_CARD.md` is stale.** It describes `synthetic/khatian_pages/` (6,000 pages, 90,650 fields, five layouts) which no longer exists on disk, and does not mention `khatian_form5462/` or `ocr_cells_packed/`. `build/package.log` shows the last `package.py` run failed (NameError at line 50), so the card and `sutro-dataset.zip` were not regenerated. Licence of `khatian_form5462/` is therefore unstated (expected MIT like the rest of the synthetic data).
2. **`sutro-dataset.zip` contains the real deed scans** (and the stale pages). It must not be uploaded to a public Kaggle dataset, GitHub or shared with judges as is.
3. **Deed scans remain in the workspace** (`sutro-dataset/real_public/dolil_deeds/`, `raw/dolil/`). They are not referenced by the app or the repo (grep found no reference), but any future bundle must exclude them unless the organisers approve an anonymised use.
4. **No trained model yet.** Kaggle run outcome unknown; two pipelines coexist (`notebooks/` torch CRNN + CNN with ONNX export, and `sutro/kaggle/sutro-bangla-digit-ocr.ipynb` TF.js digit reader used by `ocr.html`). Which one feeds the site is not yet decided in the repo.
5. **Local GPU fallback is not ready**: torch is the CPU build, CUDA wheel still downloading; the RTX 3050 has 4 GB VRAM, so the CRNN default batch 128 may need to be reduced.
6. **Synthetic pages are font-rendered, not handwriting**, and the layout is an invented "Form-5462-style" page, not a replica of a government form. OCR accuracy on real scanned or handwritten khatians is unknown and must not be claimed.
7. **Packet verification is self-consistency** (20,000/20,000 generated by rules from the same author as the engine); it is not evidence of real-world detection accuracy.
8. `kaggle/nb01/` has kernel metadata but no notebook copy beside it; whether the push script resolves `notebooks/01_...` is unknown.
9. NumtaDB is CC BY-SA 4.0: any published digit-model weights and the converted npz must carry the same licence.

## 6. Decisions

- **Data used:** synthetic `khatian_form5462/` + `ocr_cells_packed/` for the text-line OCR, synthetic `synthetic/packets` + `tables` for the evidence engine and demo, and public **NumtaDB** (CC BY-SA 4.0) for the isolated-digit model. All eligible under §8 (team-created synthetic data and clearly public open data).
- **Deeds excluded:** the DIU Dolil deed scans are not used for the app, demo, training or repo and are excluded from any shared bundle until the organisers approve an anonymised use.
- **Training:** real training runs on Kaggle GPU from the `notebooks/` pipeline; local runs are a fallback (CPU today, CUDA once the cu126 wheel is installed, with smaller batches for 4 GB VRAM). Trained runs are to be pulled into `sutro/artifacts/runs/<run_id>/` with `metrics.json`; SMOKE runs stay out of the repo.
- **Repo hygiene:** `sutro/` stays free of datasets, scans and binaries; `data/manifest.json` records what the project relies on.
